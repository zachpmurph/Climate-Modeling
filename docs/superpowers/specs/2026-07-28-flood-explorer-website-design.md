# Flood Explorer website — design

**Date:** 2026-07-28 · **Branch:** `feature-claude-website` · **Status:** initial build

## Goal

A public-facing website with two core experiences:

1. **Regions** — a browsable atlas of *simulated outcomes*: pick a region/river and an
   event stress (storm, flash-flood surge, prolonged rain…) and see the simulated
   impact — animated depth along the reach, peak depth/time/location, downstream
   hydrograph, and a plain-language narrative. A resource for looking up "what does
   event X do to river Y (in the model)".
2. **Playground** — a sandbox: pick a model (kinematic wave or 1-D Saint-Venant), set
   conditions (reach geometry, slope, roughness, inflow, rainfall), run it live in the
   browser, and watch the simulation.

Plus an **About** tab stating model provenance, verification status, and limitations
(consistent with the repo's screening-tool honesty).

## Approach (chosen): fully static, no dependencies

- Vanilla HTML/CSS/JS + inline SVG. No frameworks, no CDN, no build step — matching
  the repo's no-build-system convention and the self-contained pattern of
  `generate_flood_report.py`. Deployable on GitHub Pages or `python -m http.server`.
- **Atlas data is precomputed by the real Python solvers.** `website/build_scenarios.py`
  runs the registry solvers over a region × event matrix and writes
  `website/data/index.json` + `website/data/scenarios/<region>_<event>.json`. These
  generated JSONs are *committed deliberately* (they are published site content, like
  `docs/validation/saint_venant_2d_results.json`).
- **The playground runs faithful JS ports** of `linear_advection.run_model` and
  `saint_venant_1d.run_model` (`website/js/solvers.js`). Parity is enforced by a Node
  test (`website/test/solver_parity.test.mjs`) comparing JS output against
  Python-generated reference JSONs at tight tolerance. The site labels the playground
  as a port; the atlas as real-solver output.

Rejected alternatives: a Python web backend (requires hosting a server; the site stops
being a shareable resource) and Pyodide (authentic but a multi-megabyte, slow first
load for a small numerical core).

## Architecture

```
website/
  index.html            single page, three tabs (Regions | Playground | About)
  css/style.css
  js/app.js             tab routing + boot
  js/charts.js          SVG components: animated depth profile, hydrograph, metric tiles
  js/solvers.js         JS ports: kinematicWave(), saintVenant1D() (m-and-min units)
  js/atlas.js           Regions tab: loads data/index.json, renders scenarios
  js/playground.js      Playground tab: form -> solver -> charts
  data/index.json       generated: regions x events catalogue
  data/scenarios/*.json generated: one run per region x event
  test/solver_parity.test.mjs   node --test parity suite (JS vs Python reference)
  test/reference/*.json generated by build_scenarios.py --references
  build_scenarios.py    generator (runs the real solvers; also emits parity references)
  README.md             how to serve, regenerate data, run parity tests
```

## Regions and events (initial set)

Regions (only tracked repo data; synthetic reaches clearly labeled):

- **Columbia — Hanford Reach** (real ingested data: tracked
  `data/real_world_rivers/columbia_hanford_profile.csv`, meters-and-minutes n).
  Solver: kinematic wave (90 km reach; kinematic regime).
- **Steep Mountain Creek** (synthetic, 3 km, slopes 0.03→0.015, SI n 0.045).
  Solver: Saint-Venant (short reach; dynamic effects visible).
- **Lowland Meander** (synthetic, 20 km, slopes 6e-4→2e-4, SI n 0.03).
  Solver: kinematic wave.

Events (parameter sets scaled per region from its Manning-equilibrium baseline inflow):
`baseline`, `moderate_storm` (rain pulse), `severe_storm` (heavier rain + raised
inflow), `flash_flood` (inflow surge ×4, e.g. dam release narrative for Columbia),
`prolonged_rain` (low rate, long duration).

Scenario JSON schema: region + event descriptors, solver name, `station_m`,
`times_min`, `depth_history` (≤ ~140 frames), metrics (peak depth/time/station,
final downstream depth/discharge), mass-balance numbers, and a `limitations` list.

## Units at the UI boundary

Internally everything is meters-and-minutes (repo convention). The public UI accepts
**SI Manning n** (converted ÷60) and **rainfall in mm/h** (converted to m/min), and
displays depths in m, times in min/h. The conversion is stated in the UI.

## Testing

- **Solver parity (the load-bearing test):** `node --test website/test/` compares the
  JS ports against Python references (uniform + spatially-varying profiles, inflow,
  windowed rain) at ≤1e-8 relative tolerance. The Python suite is untouched.
- Generator smoke: `python website/build_scenarios.py` must exit 0 and validate its
  own output (finite, non-negative depths; frame counts within budget).
- Site rendering verified manually in a browser (static server, all three tabs).

## Error handling

- Atlas: fetch failures render an inline error card (site still navigable).
- Playground: input validation mirrors the Python guards (positive slope/n, CFL,
  bounded cell count ≤ 400, duration ≤ 24 h) with messages next to the Run button;
  runs execute in a rAF-yielding loop so the tab stays responsive.

## Non-goals (this iteration)

2-D scenarios in the browser, geographic basemaps in the atlas (the existing
`animate_flood_map.py` covers geo maps offline), mobile-perfect styling, deployment
automation (GitHub Actions Pages workflow can come later).
